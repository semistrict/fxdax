# Review of main, 2026-10-21

A review of fxdax's own code at 6a0a3f8 (line numbers refer to it): 22 units and 7 cross-cutting reviews, each along three dimensions, structure, performance and correctness. Every finding was checked by two independent skeptics told to refute it, and a third decided where they split. Confirmed, merged and ranked: 52 structural, 43 performance and 65 correctness issues.

## Structural issues

Items that share a root cause are grouped under one heading. Groups are ordered by their most significant item, and items within a group by severity, then by how central the code is.

### A. extentd's open-store model has no owning types: roles, registries and connection phases are runtime state that each caller checks by hand

**ExtentStore is the writer, the follower, the writerless host and the process-wide extent cache in one type (high)**
`crates/fxdax/src/extents.rs:435-466`, `:661-676`, `:687-695`, `:700`, `:705-713`, `:762-782`, `:836`, `:931-942`, `:998`, `:1030-1051`, `:1156`, `:1336-1341`, `:1436-1448`, `:1474-1479`, `:1592`, `:90-255`; `crates/fxdax/src/extentd/server.rs:241`, `:330`, `:471-479`
`following: Option<Following>` picks the role at run time. follow() builds a whole ExtentStore that shares the writer's `Arc<Store>`, and its `open`, `remote`, `profiling`, `opening` and `committed` fields go unused. About 25 sites guard with writable(), view() or `match &self.following`. The guards are uneven: cut_followers, attach_remote, flush and is_quiescent have none, and server.rs:241 compensates with `!is_follower()`. info, make_durable and uploaded read `self.remote`, while fetches go through uploader(), so a follower's INFO reports sequence_floor 0. The writer's window and open extents sit on the shared instance and outlive its connection. take_over drops `dax` but not `zeros`, which keeps the first window's size, so after a takeover with a larger window, zeros are mapped past the VMO's end.
Fix: split by lifetime into three types. `OpenStore` holds the Store, uploader, arenas, commit Event and profile. `WriterSession` holds the open extents, the opening gate and a `Window { dax, zeros }`. `FollowerSession` holds the store, a view and its window. Connection holds `enum Opened { Writer, Follower }` and refuses a request kind the role cannot serve once, at dispatch. Move the cache, eviction and relief thread into an `extent_cache` module.

**Open stores live in two registries that each operation joins by hand, and the Shuttle model covers only one (high)**
`crates/fxdax/src/extentd/stores.rs:34-45`, `:54-87`, `:91-115`, `:151-159`, `:278-285`, `:409-433`, `:487-494`, `:557-566`, `:594-599`, `:653-657`; `crates/fxdax/src/open_stores.rs:9-10`, `:79-142`; `crates/fxdax/src/store_requests.rs:256-262`; `crates/fxdax/src/extentd/server.rs:239-258`, `:396-401`, `:671-719`
PATHS (`Paths<Connection>`: a writer or a daemon hold) and INSTANCES (`Weak<ExtentStore>` plus a retired bool) share a key but have separate locks. Open, follow, retire, take_over, fork, resize, sync and stat each combine the two in their own order. retire cuts the followers and only then sets the flag (stores.rs:63-68), so a follower OPEN on followed's unheld fast path (stores.rs:95-102) can attach in between. sync and stat never re-check the instance, so they open a second ExtentStore, which waits out the 10 s flock and returns EBUSY. "Open" means that some Arc still upgrades, so FollowerStats::update's 200 ms upgrades can make Held::alone return EBUSY, the TASK-54 symptom. Teardown order is a convention (TASK-54 comment, server.rs:398).
Fix: replace both maps with one generic `Registry<H, S>` in open_stores.rs that keeps one entry per key: `Writer{holder, store} | Followed{store} | Retired{store} | Daemon`. Make each transition a method under one lock (open_writer, follow, hold_alone, live_or_hold, retire/close) that returns an RAII lease. Decide "open" from leases, not Arc counts, and extend the TASK-44.6 Shuttle model to followers, take-over and retire.

**Each control operation picks its target store, opener and hold policy inline (medium)**
`crates/fxdax/src/extentd/stores.rs:173-174`, `:217-222`, `:252-258`, `:319-321`, `:380`, `:408-451`, `:456-463`, `:481-499`, `:516-524`, `:558-583`; `crates/fxdax/src/open_stores.rs:166`, `:212-221`; `crates/fxdax/src/extentd/control.rs:283`
Take one retired store that still has followers: fork_from forks it, fork's fork_quiescent fails with EBUSY, resize grows it, and stat reports it open. `Here`, documented as "a store the daemon opened", wraps a followers' live instance in resize. open_here attaches the bucket for sync, fork and fork_from, while resize, make_public, stat and import call bare ExtentStore::open, and resize maps every open error to ENOENT. `Live`, `Forked::Live` and the raw Arcs can each be the last reference, so the blocking close (which waits on uploads) can run on an async thread, for example in sync, or in list() called from a gRPC handler.
Fix: add `resolve(key, Purpose) -> Target { Writer(lease) | Followers(handle) | Here(owned) }` on the registry, with the hold policy as an explicit parameter, and one `open_for(Purpose)` that decides bucket, arena and errno. Use a single strong-handle type whose Drop sends the last close to a blocking thread.

**A Connection's phase is spread over independent cells, and "opens once" is a check-then-set under concurrent dispatch (medium)**
`crates/fxdax/src/extentd/server.rs:320-343`, `:356-365`, `:369-378`, `:635`, `:647`, `:667-688`, `:239-259`; `crates/fxdax/src/open_stores.rs:105-118`, `:215`
dispatch runs up to 8 requests of one connection at once, so two OPENs both pass `store.get().is_some()`, both hold their keys, and both call start_behind, which overwrites the first flusher. `let _ = set(..)` then throws away the losing store and path. Teardown releases only `path`'s key, so the other key stays held under a dead Weak, and every later open, fork or resize of that store gets EBUSY until the daemon restarts. If `store` and `path` come from different OPENs, finish_connection retires the wrong key.
Fix: keep one `OnceLock<Session>` (`Writer{store, lease, flusher} | Follower{store, teller}`) set under a mutex, or handle OPEN on the receive task before dispatching anything else. Declare the lease after the store, so "store gone before path released" follows from field order.

**Process-wide extent-cache entries keep the context of whichever store asked first (medium)**
`crates/fxdax/src/extents.rs:100-103`, `:131-137`, `:257-309`, `:1110-1126`, `:1253-1258`, `:1652-1654`, `:1688-1716`
cached() builds each entry from the caller's Store, fetcher and recorder, and every later user pages in through them. free() removes the entry only when the entry's store is its own. So when fork A, which created the entry for inherited extent X, frees X, fork B's next page-in after eviction goes through A's store and gets NoExtent: one tenant's FREE breaks another tenant's reads. The boot-profile recorder records other forks' page-ins and misses its own. Callers lock the map and build `(arena, extent)` keys themselves.
Fix: an `extent_cache` module with a private map and a small API: `get(arenas, extent, len)`, `forget_from`, and `insert_sealing`, atomic with creation. Page in through a lineage-level reader keyed by extent ID, and record profiles at the store's own read and map entry points.

**Five locks and the opening gate are ordered by convention, and fork() leaves "no change meanwhile" to its caller (medium)**
`crates/fxdax/src/extents.rs:437`, `:451-453`, `:689`, `:853-856`, `:1079`, `:1224-1258`, `:1500`, `:1582`, `:1689-1716`; `crates/fxdax/src/extentd/server.rs:567-571`
Only "open before dax" is written down. The real order is opening → open → dax → cache `extents` → `allocators`, and cached() can block on another guest's seal while it holds open and dax, which is safe only by an unstated argument. A read-only map_open creates an OpenExtent without the gate, and take_over checks is_quiescent without it. A FORK without FORK_QUIESCENT calls the unguarded fork, which can land between commit_ordered and the `sealing` publication.
Fix: put the open-extent table and the window under one writer-state mutex. Add gate tokens: `Gate::open() -> Opening`, required to insert or write, and `Gate::quiesce() -> Quiesced`, required by fork and take_over. Move cached()'s cross-store wait out to its callers.

### B. extent_store's commit State has no sub-owners

**commit_locked is one 220-line transaction over a ~39-field State, failure poisoning is set by hand, and one step misses it (high)**
`crates/extent_store/src/store.rs:288-377`, `:1805-2026`, `:1828`, `:1858-1881`, `:1889`, `:1898`, `:1952`, `:1971`, `:2248-2260`
Views, uploads, segments, framing, the index, the lineage and fork freezing all advance in one function body, with nothing marking which steps can be undone. `failed = true` is set by hand at 1828, 1889, 1952 and 1971. The `?` at 1898 (`segment_file`) returns without setting it, although by then changes were taken, `open` was cleared, views were published, a Committed was queued and the window was updated. The next commit then reuses the epoch, publishes it to views a second time, and never indexes the lost changes. Today this cannot happen only because close_idle_files skips dirty segments (1313).
Fix: split State into sub-structs (Space, OpenWrites, Segments, IndexLog, UploadLog, ViewKeeping, Reaper) and make the commit a short series of phase methods on them. Run everything after the first mutation in one closure, or under one drop guard, that sets `failed` once, as close_now does.

**The segment lifecycle is implicit in Option fields and list membership (medium)**
`crates/extent_store/src/store.rs:285`, `:327`, `:379-395`, `:1303-1321`, `:1907-1931`, `:2128-2195`, `:2215`, `:2232-2269`, `:2330-2343`
A segment's phase is the combination of `file`, `closed` and `framing`, plus membership in State.framing, Pending.framing, dirty_segments, uncovered and unuploaded. close_open_segment(now=true) dooms the raw file and marks it dirty. close_now, its only now=true caller, then un-dooms that file and deletes it itself. A framing segment's raw file is protected only by the framing thread's clone against close_idle_files' `strong_count == 1` test. Footer chaining keeps both `last_closed` and `footing.after`.
Fix: a `Segments` module with `enum Phase { Open, Framing, Closed }` (plus inherited) and transition methods (close, framed, syncable, reap). Pending carries Closing tokens, and one footer-chain cursor replaces the two counters.

**"Last durable epoch" has no single value, and callers derive it from pending.len(), which cannot see an in-flight flush (medium)**
`crates/extent_store/src/store.rs:217-218`, `:1243-1251`, `:1743`, `:2319-2382`, `:2394-2397`; `crates/fxdax/src/remote.rs:775-779`; `crates/fxdax/src/extentd/server.rs:225-230`, `:836-843`
flush drains `pending` before it syncs. So upload()'s `epoch - pending.len()` and close()'s `flush_pending()` count drained but unsynced commits as durable. This is safe only because the uploader flushes right after upload(), and extentd stops flush_behind before close. Uploads.durable and the lineage keep further copies.
Fix: a `Durability { ordered, durable, queue, in_flight }` type with push, take_batch, finish and is_pending. upload() and close() read from it.

**Index-log logic is spread over free functions, open_in and commit_locked (medium)**
`crates/extent_store/src/store.rs:334-346`, `:532-538`, `:675-685`, `:696-730`, `:866-875`, `:1062-1070`, `:1925-1998`, `:2358`
The newest-checkpoint scan is written in both recover and rebuild. The checkpoint is built both by Recovered::checkpoint and inline in commit_locked. Retained index files are split into pinned and doomed twice, in open_in and in commit_locked. The checkpoint trigger depends on `uncovered`, which segment reaping fills.
Fix: an `index.rs` with an `IndexLog` that owns number, file, len, deltas, retained, checkpointed, checkpoint_wanted and uncovered, with `open` and `append -> IndexWrite`, one newest_checkpoint helper and one checkpoint constructor.

### C. DAX sealing

**The seal remaps from a stale private list instead of Dax's own index (high)**
`crates/fxdax/src/dax.rs:350`, `:362-369`, `:449-453`, `:533-536`, `:552-562`, `:585-604`; `crates/fxdax/src/extents.rs:430-431`, `:1293-1319`, `:1525`, `:1538`, `:1563-1568`, `:1597-1602`, `:2027`
Every MAP appends to OpenExtent.mappings, before dax.map even runs, and UNMAP, remaps and FREE never remove anything from it. seal_mapped walks that list and relies on make_read_only's `is_kept`, which matches the open VMO at any offset. If range W was remapped to offset Y of the same open extent, the stale (W, X) entry passes `is_kept` and seals E@X over W, and the (W, Y) entry is then skipped. The guest reads the wrong bytes, and window_mappings records them for snapshots. Separately, Window::map replaces the VMAR mapping before a populate that can fail, and Dax::map then returns before forget/insert, so its records still name the old keep. Not yet confirmed: whether today's guest issues such a remap.
Fix: add `Dax::remap_kept(identity, |start, end, &K| ..)`, driven by `kept[identity]`, that takes the sealed offset from the Mapped record (`offset + (start - window_offset)`). Delete make_read_only, `is_kept` and OpenExtent.mappings. Make populate best-effort, so the records are updated whenever the mapping is replaced.

### D. Guest DAX write path: gate, lock and allocation-scope contracts are comments

**The seal-count/gate protocol is open-coded at four sites, and its preconditions exist only in comments (high)**
`guest/linux/fs/fxfs/dax.c:46`, `:252`, `:264`, `:400`, `:479-486`, `:509-537`, `:930`, `:944`, `:1037`, `:1091`, `:1154-1185`, `:1572-1634`, `:1994-2006`; `guest/linux/fs/fxfs/device.c:18-33`; `guest/linux/fs/fxfs/device.h:78`, `:107`
The sequence "read seals, call Rust, check open, enter the gate, compare, else leave and retry" is copied into map_chunk, new_slice, iomap_write and restage_work. "In the gate" appears only in comments. map_to and reach claim it unconditionally, yet they run outside the gate for sealed extents. The gate is a hand-rolled counter that lockdep cannot see. "Rust is called holding no gate" can be checked only by tracing every goto.
Fix: a ticket API, `fxfs_device_store_ticket` plus `fxfs_device_store_enter(dev, ticket, nowait)` returning 0, -EAGAIN or -EBUSY, and one `fxfs_dax_find_open` loop helper. Give the gate a lockdep_map, and add `fxfs_device_assert_storing` and `fxfs_device_assert_not_storing` checks.

**fxfs_dax_iomap_write mixes six concerns in 167 lines (medium)**
`guest/linux/fs/fxfs/dax.c:1409-1425`, `:1512-1678`, `:1703-1704`; `guest/linux/fs/fxfs/fxfs.h:325-332`
Preparing a fresh chunk throws away the extents map_write returned, and they are read again. The zeroing short-cut sits inside the retry loop. Held-page save, move and restore uses two preservation mechanisms (Rust's keep=true and C's held copy). `size` doubles as a "grows" flag. The function returns holding the gate, flagged by IOMAP_F_PRIVATE, and its error path writes the held page back through Fxfs. A new exit has to get all three rules right.
Fix: split it into write_range, open_pages (built on the ticket helper), a `struct fxfs_dax_held_page`, and fill_write_iomap. Reuse map_write's extents.

**invalidate_lock has three different contracts across the vfs.h DAX hooks (medium)**
`guest/linux/fs/fxfs/vfs.h:236-269`; `guest/linux/fs/fxfs/dax.c:1752-1762`, `:2264`, `:2363-2451`; `guest/linux/fs/fxfs/super.c:701-719`, `:948-972`, `:1782-1790`, `:2276-2300`
resize_begin and punch_begin take the lock inside dax.c and release it themselves on error. remap, shrunk and changed-with-an-inode require the caller to hold it. changed-without-an-inode takes it itself. Page-cache resize takes no invalidate_lock at all, and dax.c keeps a second copy of the resize sequence that goes through a different Rust call.
Fix: make super.c the owner of the lock for every size, punch, remap and settle change. Turn dax.c's hooks into plain functions that lockdep_assert_held_write, and have dax.c's write path call fxfs_vfs_resize.

**The rule that every call into Rust runs NOFS is kept by hand at about 50 C call sites (medium)**
`guest/linux/fs/fxfs/super.c:7-8`, `:1288/1306`, `:1397/1431`, `:1628/1630`, `:1641/1643`, `:1850/1852`, `:2478/2480`, `:1967`, `:2165`, `:2342`, `:2344`, `:2444`; `guest/linux/fs/fxfs/vfs.h:25-31`; `guest/linux/fs/fxfs/dax.c:248`; `guest/linux/fs/fxfs/rt.c:25-36`, `:137-141`; `guest/rust/linux-rt/src/executor.rs:21-32`
About 45 fxfs_nofs() wraps, 6 manual memalloc_nofs pairs, and several unwrapped calls whose safety depends on what the Rust side allocates. fxfs_rt_alloc is a plain GFP_KERNEL allocation with no assertion, so a missed wrap shows up only as a reclaim deadlock under memory pressure.
Fix: enter the scope once on the Rust side. linux_rt::block_on and the few synchronous entry points hold an fxfs_rt_nofs_save/restore guard, as rt.c already does for worker items. Then delete the C wraps.

### E. doc-7 replication: the chain rules are kept twice, and the simulation runs the copy production doesn't use

**Segment footers come from two producers, and segment numbering is synced by hand in four places (high)**
`crates/extent_frame/src/segment.rs:21-45`; `crates/extent_remote/src/writer.rs:51-57`, `:235-311`, `:264-272`, `:316-346`; `crates/extent_store/src/store.rs:173-178`, `:2128-2175`; `crates/fxdax/src/remote.rs:763-782`, `:820`, `:849-858`; `crates/extent_remote/src/sim/world.rs:469-608`
Writer::close and Store::close_open_segment each stamp seq, after, own keys and next_sequence, using different formulas. remote.rs predicts close's numbering to seed Footing, then asserts the prediction. In steady state production sends every segment through add_segment. The simulation, doc-7's proof, drives only commit, close and fork, and replays commits where production diffs a snapshot, so the store's footer code never runs against takeovers or collectors. Traced but not reproduced: a store footer's next_sequence can cover an own extent that only the next segment names (close_now between commits). The collector can then delete that extent as an orphan between its PUT and its segment's PUT (collector.rs:263-270, 317-318). Drift in seq or after fails closed in add_segment.
Fix: one `segment::Chain { branch, epoch, next_seq, after, sequence_floor }` with `close(contents) -> Footer` and `admits(&Footer)`, used by the Writer, the store and add_segment. Drop remote.rs's prediction, and drive the simulation through extent_store and add_segment.

**There are two extent-read stacks, and the simulation checks reads through the one production doesn't use (medium)**
`crates/extent_remote/src/reader.rs:273-299`, `:336-348`; `crates/extent_remote/src/fetch.rs:246-290`, `:471-490`; `crates/extent_remote/src/layout.rs:231-288`; `crates/extent_remote/src/checkpoint.rs:7-8`, `:41-82`; `crates/extent_remote/src/sim/world.rs:913`, `:930`
reader::read and Fetcher::read each have their own copy of the moves loop (the MOVES bound, Lost on No or Dropped) and of the tail check. Production reads only through Fetcher. checkpoint::Table has no production caller, though checkpoint.rs and doc-7 describe hosts using it.
Fix: one object-reading module under Fetcher with the moves loop written once. Make reader::read a call to Fetcher with no cache. Wire checkpoint::Table into a caller or delete it.

**Error::Reopen is documented as recoverable, but every caller treats it as fatal (medium)**
`crates/extent_remote/src/lib.rs:48-51`; `crates/extent_remote/src/writer.rs:133-160`, `:373-380`; `crates/fxdax/src/remote.rs:168-175`, `:380-383`, `:636-673`
The case is reachable. Writer::open lists the segments before placing its fence, so an earlier writer's in-flight segment can land at the new writer's next seq. The uploader folds Reopen into Other and fails for good, so every later commit on that store fails. The closed segments' footers are already stamped, so a restart would also have to re-stamp them.
Fix: on Reopen, discard the store's segments framed for the old position, rerun start(), and model that in the simulation. Otherwise, make Reopen terminal and document it as such.

**The uploader keeps in-flight segments in five parallel records, aligned by position (medium)**
`crates/fxdax/src/remote.rs:56-64`, `:586-606`, `:818-839`, `:851-856`, `:866-930`; `crates/fxdax/src/extents.rs:862`, `:914`; `crates/extent_store/src/store.rs:2163`; `crates/extent_remote/src/writer.rs:386-420`
The records are the FuturesOrdered `uploads`, a Vec `uploading` popped with remove(0), the on-disk marker (rewritten at six sites in two files), Writer.pending and store.unuploaded. They stay aligned only because each footer carries exactly one commit tag. One acknowledge() can ack several segments, while acknowledged() pops only the head.
Fix: an `InFlight` type that owns a `VecDeque<Segment{seq, epoch, number, tag}>` and the upload futures, a `Marker` type, and one write_durably helper.

**Remote::fork doesn't fork: it is a second completion channel for "segment acknowledged" (medium)**
`crates/fxdax/src/remote.rs:471-485`, `:593-618`, `:647-650`, `:679-699`, `:716-726`; `crates/fxdax/src/extents.rs:853-865`; `crates/extent_remote/src/writer.rs:386-440`
Store::fork makes the fork. Remote::fork queues (child, sender), and the run loop answers from two sites with `writer.state().last_commit` as of the answer. If a later commit is acked in the same acknowledge(), the child's marker records a later tag, and start() then refuses the child as "moved on elsewhere". With overlapping forks, one can be answered "the store made no fork" while its segment still uploads, and record_forks then creates a bucket record for a child that was deleted.
Fix: have Store::fork return the fork epoch. ExtentStore::fork waits on uploaded(fork_epoch) and writes the marker with the fork commit's own tag. Delete Progress.forks, Forked, `forking` and Shared::fork(all).

**The store builds and queues a per-commit Committed that the uploader drains and throws away (medium)**
`crates/extent_store/src/store.rs:148-156`, `:216`, `:1750-1759`, `:1860-1880`; `crates/fxdax/src/remote.rs:810-811`
Since TASK-29.2 the footers carry this information. committed() is called only to keep the queue from growing, and only the unreleased byte count is used.
Fix: remove Committed, Uploads.committed and Store::committed, and keep `unreleased.insert(epoch, bytes)`. Rewrite the tests to inspect closed segments' footers.

### F. Guest Rust delayed unlinks

**The inode-drain rule is applied by hand per op, and lookup and exchange miss it, handing the kernel stale link counts (high)**
`guest/rust/fxfs-linux/src/fs.rs:195-199`, `:248-255`, `:609`, `:693-699`, `:1019-1029`, `:1053-1055`, `:1221-1232`, `:1244-1254`; `guest/linux/fs/fxfs/super.c:131`, `:201`, `:666-680`, `:1851`
Each op lists the inodes it drains. lookup drains `dir` but not the child whose attributes it returns. exchange drains dir and new_dir but not a and b, and then reports their nlink. A worker wakes only once 32 unlinks are queued, so a few can sit queued indefinitely. The kernel's nlink stays high, so evict passes unlinked=false, and the object reaches the graveyard but is never tombstoned: space leaks until remount, and st_nlink is wrong.
Fix: drain in the accessors. `directory(dir)` drains dir, a new `child(dir, name)` drains the inode it finds, and `name_transaction(inos)` drains before it takes the locks. setattr keeps the non-draining transaction.

**The delayed-unlink engine lives inside Fxfs, and its workers hold a raw `*const Fxfs` (medium)**
`guest/rust/fxfs-linux/src/fs.rs:182-290`, `:219-224`, `:331`, `:493-498`, `:1282-1315`, `:1363-1368`; `guest/rust/fxfs-linux/src/lib.rs:262`, `:273`, `:289-293`
FxfsRef carries a hand-written `unsafe impl Send`. Fxfs must not move or drop between the first unlink and stop_delayed, and only a comment says so (lib.rs:289). The public Fxfs::unmount doesn't stop the workers. Their lifecycle is spread over three flags, and the `pending` and `applying` counters are changed from outside the queue type.
Fix: move the engine into `delayed.rs` as `DelayedUnlinks` behind an Arc that owns the queue, its events, the ObjectStore, the FxFilesystem and the directory cache. Replace the flags with one lifecycle enum, give the queue the methods that keep its counters, and have Fxfs::unmount stop it.

### G. fxdax's allocator changes in ported Fxfs

**The allocator's extent lifecycle is an implicit state machine over eight collections and two apply modes (high)**
`crates/fxfs/src/object_store/allocator.rs:524-526`, `:632-650`, `:787-818`, `:870-873`, `:957-966`, `:1059-1074`, `:1110-1113`, `:1301-1339`, `:1571-1580`, `:2224-2235`, `:2371-2390`, `:2433`; `crates/fxfs/src/fsck.rs:551`
Whether an extent is alive, empty but pinned, dead, freed but unsealed, sealing or dying is implied only by which of `extents`, `shared`, `staging`, `dead`, `unsealed` and `sealing` it is in, plus two byte totals. Three callers must remove the extent and subtract its bytes before kill(), and other sites kill extents that were never in `extents`. Replay and live operation follow different death rules. Inner::unpin merges an unjournaled tombstone under the lock, while deallocate_part returns its tombstone for apply_mutation to merge. A missed update makes unavailable_bytes drift, so NoSpace is misjudged until fsck reports ExtentMismatch.
Fix: an `ExtentTable` module with an explicit `enum ExtentState` and transition methods that return the tree records they imply. Then only apply_mutation and the one restage entry point write the tree. Use one replay rule.

**Which frees a barrier seals is tracked separately by the device, the allocator and the journal (medium)**

## Performance issues

**Shared root cause (1-4): extent_store does blocking file I/O inside critical sections that every request of the store, or of the lineage, takes.**

**1. `close_now` frames and fsyncs the open segment while holding `committing` and `state` (high)**
Locations: crates/extent_store/src/store.rs:2233-2256, 2186-2190, 449-467; crates/fxdax/src/remote.rs:807-809
Every gather in the uploader calls `close_now` (remote.rs:807-809). It takes both locks (store.rs:2233-2234), and while holding them it reads back, zstd-compresses and writes everything since the last close (2249 → 2186-2190 → 449-467), then runs an fdatasync, two directory fsyncs and a barrier (2250-2254). bab5ac8 moved framing off commits but left this one in place. While it runs, the store serves no WRITE, COMMIT, FREE, READ or page-in. In pgbench-tps on GCS (gce-fs-bench-frame-2026-10-21T0301Z) there were 113 closes at 58.1 ms each, about 38 per iteration against 43 durable commits, so most are `close_now`'s: about 2.2 s per iteration with the store frozen. Verifiers agree that other requests stall. They disagree on how much this lengthens the durable wait itself, because its PUT needs the framed object anyway.
Fix: close through the Framing path, as commits already do. Call `close_open_segment(.., false)`, drop both locks, wait for the framing and sync with no lock held, then re-take `state` only to install the result. To shorten the durable wait as well, frame each 1 MiB part as it fills (`Packer::push`, crates/extent_frame/src/lib.rs:190-193), so a close packs only the tail. Pass the framed bytes to `Closed::bytes` instead of reading them back from disk.

**2. Seal reads back and rewrites every extent that took more than one WRITE, while holding the store's locks (high)**
